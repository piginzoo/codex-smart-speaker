# 03 · 踩坑全记录：一次真实开发的完整排查史

> **本文档是本仓库最值钱的资产。** 它按时间顺序完整记录了从零到交付过程中遇到的每一个问题：现象 → 排查过程 → 根因 → 修复 → 教训。后续迭代者（人类或 AI）在动手之前**必须先读完这篇**，避免重蹈覆辙。
>
> 排查方法论提示：本文所有问题都遵循同一套路——**先取证（日志/截图/dumpsys），再假设，再实验验证，最后才改代码**。凡是跳过取证直接改代码的轮次，都被用户批评过"想好了再干"，见 #14。

---

## #1 环境搭建：APK 从哪来？（国行无 Play 商店）

- **现象**：手机是国行固件，没有 Play 商店，ChatGPT 装不上。
- **排查/方案**：用 [apkeep](https://github.com/EFForg/apkeep)（命令行 APK 下载器）从 APKPure 拉包。
- **坑 1**：apkeep 的参数语义——`-a` 是 App ID、`-d` 是下载源（写反了会报 "invalid value for --download-source"）；从 apk-pure 源下载必须加 `-o 'acknowledge_dangers=true'`（APKPure 有过篡改 APK 前科，工具强制要求表态）。
- **坑 2**：下载下来的是 **.xapk**（base APK + 按架构/语言/密度拆分的 split APK 的 zip 包），不能直接 `adb install`，要解包后 `adb install-multiple`。
- **坑 3**：apkeep/网络下载大文件**经常截断**——`unzip` 报 "End-of-central-directory not found" 八成是文件没下全，`ls -lh` 看大小 + `file` 看类型即可识破；重试即可。
- **安全动作**：装前必验签。`apksigner verify --print-certs` 比对签名 SHA-256 指纹，与 Play 官方代签证书（`b24f4bfb...`）一致才入库。**验签动作贯穿全程，每个版本的包都验过。**
- **教训**：第三方源的包一律验签；xapk 要解包；工具的强制确认参数先看 help。

## #2 版本兼容：最新版 ChatGPT 根本装不上 Android 9

- **现象**：拉到最新版 ChatGPT（1.2026.307），xapk 的 manifest.json 写着 `min_sdk_version: 29`（Android 10），本机是 Android 9（API 28）。
- **排查**：用 apkeep 的 `-l` 列出全部历史版本，**从新到旧二分探测**每个版本的 minSdk（每次只解包读 manifest.json，不浪费流量）：1.2026.307=29 → 1.2025.350=29 → 1.2025.322=**23**（✅，且带 arm64_v8a）。
- **转折**：后来发现根本不用人肉找版本——装好 Play 商店并登录后，商店页面的"**通过 Play 更新**"按钮会把侧载版就地升级成 **Play 正渠道版**，且 Play 会**自动挑选设备兼容的最高版本**（最终装上了 1.2026.314，比 APKPure 源还新一版）。这是本项目的最佳实践。
- **教训**：①Android 安装器强制执行 minSdk，装得上就说明兼容；②能让 Play 自己管理版本就不要手动管；③二分探测 + 只读 manifest 是省钱探测法。

## #3 PairIP 校验：App 一启动就 "Something went wrong"

- **现象**：ChatGPT 启动后焦点停在 `com.pairip.licensecheck.LicenseActivity`，弹窗 "Check that Google Play is enabled..."，点 CLOSE 直接被弹回桌面（**致命，不是警告**）。
- **背景知识**：PairIP 是 Google 的 Play 应用防篡改/授权校验组件（反逆向 + 授权检查），2024 年起大规模铺开。
- **排查**：验证"是不是只有新版本带 PairIP"——下载历史版本逐个扫 dex 找 `com/pairip` 引用。
  - **坑**：第一轮只扫了 `classes.dex` 得出 "0 hits" 的**假阴性**结论（大 APK 有 classes2~6.dex），差点误判 1.2024.352 无 PairIP；装机实测立刻打脸。修正：**用 Python 对所有 `classes*.dex` 全量扫字节**。
  - 结论：1.2024.289（36 处引用）、1.2024.352 全带 PairIP → **所有带语音功能的版本都过不了，老版本路线判死**。
- **决策**：征得用户同意，安装 GMS 三件套（用户明确表态"不介意装 Google 服务"）。
- **结果**：GMS 装完 + 重启后，PairIP 放行（第一次到 ChatGPT MainActivity），但随即跳转 Play 商店要求"从 Play 获取此应用"→ 见 #5。
- **教训**：①扫 dex 要扫全；②PairIP 是拦路虎时，装 GMS + Play 渠道安装是正路，改包绕过是邪路（安全风险 + 违反 ToS）。

## #4 GMS 安装：GSF 版本、账号、重启玄学

- **坑 1**：APKPure 的 GSF（com.google.android.gsf）最新版 minSdk 是 Android 10（`sdkVersion:'Q'`）——Android 9 装不上；但实测 **GSF 可以先不装**，Play 服务（26.45，minSdk 24）+ Play 商店（52.9，minSdk 24）两个用户级 App 就够过 PairIP 和登录。
- **坑 2**：登录 Google 账号后系统要求**重新验证密码**（未认证设备的例行风控），这步必须用户本人在手机上输入。
- **坑 3**：brew 装 JDK 的 cask（temurin@17）要 sudo 密码，沙箱环境拿不到——换 `brew install openjdk@17`（formula 不需要 sudo）。
- **教训**：无 root 装 GMS 走"用户级 App"路线在三星上可行；密码类交互永远交给用户本人。

## #5 "从 Play 获取此应用"：侧载版不被 PairIP 认账

- **现象**：GMS 就位后启动 ChatGPT，弹出 Play 的横幅页"**从 Play 获取此应用**——若要继续使用 ChatGPT，请前往 Google Play 下载该应用"。
- **根因**：PairIP 的授权检查不仅要求"机器上有 Play"，还要求**这个 App 是从 Play 渠道装的**（我们的是侧载）。
- **修复**：在 Play 商店的 ChatGPT 页面点"**通过 Play 更新**"（Play 认得我们的包——签名一致），Play 自动拉取设备兼容的最高版本并就地转为 Play 渠道。此后 PairIP 永久放行，且以后升级走商店自动管理。
- **教训**：PairIP 的三个门槛 = Play 服务在场 + Play 已登录 + App 来自 Play 渠道。**让 Play 接管版本管理是终局解**。

## #6 坐标系统：屏幕方向 + QHD/FHD 双重陷阱

- **现象**：对着截图算好的坐标点"通过 Play 更新"按钮，连点三次毫无反应。
- **排查**：`sips -g pixelWidth` 看截图尺寸——**2220×1080，横屏！** 而 `adb shell wm size` 显示 Override size = **1080x2220**（FHD+），物理面板是 1440x2960。
- **根因（两层）**：
  1. 三星默认 **FHD+ 渲染**（省电），`input tap` 用 Override 尺寸坐标系，不是物理 QHD；
  2. **坐标系随屏幕方向旋转**。手机横放时 x∈[0,2220]、y∈[0,1080]，按竖屏习惯算坐标必然落空（y>1080 直接越界无效）。
- **修复**：所有屏幕交互前先 `wm size` + 看截图尺寸确认方向；把手机回正竖屏后再测。
- **教训**：**adb 自动化里永远不要用"看截图目测坐标"**——要么 uiautomator dump 拿 bounds，要么先确认分辨率+方向再算比例。截图是 2220 宽还是 1080 宽本身就是方向探针。

## #7 uiautomator dump 在动画页面失效

- **现象**：ChatGPT Live 会话页（蓝球常驻动画）执行 `uiautomator dump` 报 `ERROR: could not get idle state`，拿到的是过期旧页面。
- **根因**：uiautomator dump 需要 UI 进入"空闲"状态才能输出，动画永不空闲。
- **修复**：放弃 uiautomator 作为运行时工具（保留它做静态页面勘察），**运行时读屏一律用自研管家 App 的 AccessibilityService**——a11y 事件是推送式，不需要页面空闲。
- **教训**：uiautomator dump 只适合静态页面；动态页面（动画/视频/实时内容）要靠 AccessibilityService 的窗口内容事件。

## #8 无障碍服务绑定玄学（三星特供）

- **现象（多重）**：
  1. `settings put secure enabled_accessibility_services` 后服务**没有绑定**（`dumpsys accessibility` 的 `bound services:{}` 为空）；
  2. `adb install -r`（覆盖安装）会**清空**该设置项；
  3. 把设置项从服务 A 换成服务 B 再换回来（toggle 大法）、组合开关 `accessibility_enabled` 0/1，均**不触发重绑**；
  4. **重启手机后绑定成功**；且后来发现：**刚重启完的"干净状态"下 settings put 直接生效**（不用重启）。
- **修复**：沉淀成 `setup_butler.sh`——装机后必跑（授予麦克风、写 a11y 设置、电池白名单、熄屏/亮度配置），**跑完重启一次**；文档写明"三星需要重启让服务重新绑定"。
- **教训**：三星 One UI 对无障碍的 Settings.Secure 注入支持不完整，reboot 是兜底但不是每次必须；**每次装机后先 `dumpsys accessibility | grep -A4 "bound services"` 验证绑定**，别等服务不工作才发现。

## #9 Compose 界面无标识：UI 自动化策略的四轮进化

- **现象**：要在 ChatGPT 主页自动点击右下角蓝色"语音模式"按钮，但 `AccessibilityNodeInfo` 树里**所有节点 `contentDescription=null, text=null, viewIdResourceName=null`**——ChatGPT 是 Jetpack Compose 构建，Compose 节点默认不向无障碍暴露 id/语义（除非开发者主动设置 semantics）。
- **教训先行**：用户提议"找到组件 ID 直接触发"——方向正确，但在 Compose 上**没有 ID 可找**，这是本次开发最重要的现实约束之一。
- **策略进化史**（每一轮都被真机打脸）：
  1. **desc/text 匹配**："语音模式/voice mode"——全 null，失败；
  2. **resource-id 匹配**：null，失败；
  3. **位置兜底 v1**（下半屏右半区最大可点击节点）：蓝色按钮中心在屏幕 **43.5% 高度**，被"cy>55%"阈值筛掉——**阈值拍脑袋，先测量再定阈值**；
  4. **位置兜底 v2**（放宽到 cy>35%，取面积最大）：三个候选节点等面积（144×144 的 mic 图标和蓝按钮），遍历顺序先到 mic 图标——**等面积时"最大"无区分度**；
  5. **位置兜底 v3**（取最靠右）：撞上一个 **12px 宽的滚动条竖条**（x=1032-1044）——没有尺寸下限的"最靠右"必被细长条劫持；
  6. **终版**：右下区域 + **宽高都在 100~300px 之间的方块** + 取中心 x 最靠右者。蓝按钮 144×144 恒定命中（键盘弹起时按钮在 43% 高度、收起时在 88% 高度，均命中）。
- **配套实践**：加"先看后点"——进入点击阶段前先 `Log.d` 打印整棵可点击节点树（desc/text/id/bounds），第一轮不点只记录；点击前也 log 节点详情和 performAction 结果。
- **教训**：①**Compose 应用做 UI 自动化，语义匹配基本不可用，位置+尺寸启发式是唯一现实路径，但必须用"可点击节点树 dump 日志"先侦察再定策略**；②启发式每一版都要有"为什么会被打脸"的记录；③点击动作必须留日志（点了什么、结果如何）。

## #10 "呼出后 5~8 秒就消失"：a11y 瞎点 + 兜底逻辑拆台

- **现象**：用户观察——ChatGPT 被唤出后在屏幕停留 5~8 秒就消失回桌面。
- **排查**：日志显示 `点击语音按钮: d=null t=null id=null b=Rect(750,...)`——点的是 **mic 图标不是语音按钮**（v2 策略的等面积问题），且旧代码里还有一个 **20 秒兜底**（进语音失败就 goHome）和一个**"会话结束检测"**（靠找"关闭/结束"类文字按钮判断是否还在语音 UI——Compose 无文字，永远找不到 → 6 次事件后误判"会话已结束"→ 强行回桌面）。
- **根因**：三个机制叠加拆台：点错按钮 + 兜底放弃 + 误判结束。
- **修复**：
  1. 删除整个 UI 版"会话结束检测"（见 #12 换成音频模式信号）；
  2. 点击策略进化到 v6（见 #9）；
  3. 兜底保留但只在"确实没点上"时触发。
- **教训**：**兜底逻辑也是逻辑，它会在正常流程之外独立触发**——每写一个 fallback 都要问"它在什么情况下会误伤正常流程"。用户的人肉观察（停留几秒消失）是定位这类"多机制叠加"问题的金线索。

## #11 ★Live 连不上：管家的麦克风监听把 ChatGPT 饿死了（本项目最大坑）

- **现象**：一切自动化都通了（亮屏→拉起→点进语音模式），但 **Live 的大蓝球永远转圈，连不上**。用户手动测试文本聊天正常，语音不通。用户原话："它的消息是通的，但是它 live 没有弹出那个大大蓝框"。
- **关键时间线对照**：**上午 10:29 用户手动测试语音是好的**（那时管家 App 还没装机）；装机后 live 就再没连上过。变量隔离指向管家 App。
- **日志取证**（决定性证据）：
  - `APM_AudioPolicyManager: startOutput() VOIP CALL ON`（11:29:18 live 开启）
  - `WebRtcAudioRecordExternal: Number of active recording sessions: 1`（**只有一路录音在活动——是管家的**）
  - 44 秒后：`WebRtcAudioTrackExternal: underrun count: 2 → stopThread → releaseAudioResources`（**ChatGPT 的 WebRTC 音频饿死自杀**）
- **根因**：管家的"24 小时监听唤醒词"循环持有一个 `AudioRecord`。**三星 Android 9 上麦克风先到先得**——管家先注册，ChatGPT 的 WebRTC 录音拿不到真实音频流，上行静音 → Realtime 会话建立失败 → 蓝球转圈 → 超时断开。此前"麦克风是共享的"的判断（`micHeld=false`，rms 有读数）恰恰是假象：**共享到的是"我的流活着"，代价是 ChatGPT 的流被饿死**。
- **修复（架构级）**：
  1. **会话期间对象级释放录音器**——`AudioRecord` 直接 stop/release/置 null，不是暂停；ChatGPT 独占麦克风；
  2. 监听循环改为：`sessionActive=true` 时不打开任何录音器，纯 sleep 轮询；
  3. 挂断检测从"麦克风循环里顺带查"拆成**独立看守线程**（每秒查 `AudioManager.mode`，不碰麦克风）；
  4. 会话结束 → `micRestartRequested=true` → 循环重建全新录音器（防音频路由残留）。
- **验证**：修复后首次实测，大蓝球出现，live 一次连上。
- **教训**：⭐ **"两个 App 都能录音"≠"两个 App 都录得好"。在三星设备上，后到的实时音频管线（WebRTC）会被先到的录音饿死。凡是"自己 App 常驻录音 + 别的 App 也要录音"的设计，必须在对方会话期间彻底让出麦克风。** 这个坑的排查思路：时间线对照（什么时候开始坏）+ 底层日志（AudioFlinger/WebRTC）+ 变量隔离（管家装与不装）。

## #12 会话结束检测：UI 判据全灭，音频模式是唯一真信号

- **演进**：
  1. v0 设计"读字幕找拜拜"——被需求变更砍掉（用户实测 live 自带语音挂断）；
  2. v1"找'关闭/结束'文字按钮判断语音 UI 是否消失"——Compose 无文字，永不命中，**误判频发**（见 #10），删除；
  3. v2 麦克风归还信号（被抢占后恢复稳定读取=挂断）——在"麦克风被抢"场景有效，但 #11 修复后管家根本不再持有录音器，此信号失去前提；
  4. **终版：独立看守线程每秒查 `AudioManager.mode`**。ChatGPT live 开启时系统音频进入 `MODE_IN_COMMUNICATION`（值=3），用户挂断后回落 `MODE_NORMAL`——**连续 5 秒回落即判会话结束**。此信号：不依赖 UI、不占用麦克风、100% 可靠（实测多次）。
- **教训**：①判断"某 App 是否处于语音通话态"，`AudioManager.mode` 是 Android 上最可靠的系统级信号；②UI 文字判据在 Compose 应用上是死路；③检测逻辑与业务主循环解耦成独立线程，各自简单。

## #13 唤醒词识别：合成音的识别率只有 2/3

- **现象**：Mac `say` 合成音喊 "Hey Codex!"，Vosk（small-en-us-0.15）的 partial 输出时而 "hey codex"（命中），时而 "hey go that" / "presented kodak's"（不命中）。
- **修复**：唤醒词从单词匹配改为**变体表**：`codex / kodak / kodaks / codecs / codaks / codexs`（切词后精确匹配任一）。日常中文对话误触风险极低（这些词中文语境几乎不出现）。
- **实测**：英文闲聊 + 中文聊天零误触（maybeTrigger 计数 0）。
- **教训**：①离线小模型的唤醒词识别要按"**变体白名单**"做，不是精确匹配；②用 `say`/TTS 当测试声源是个低成本联调妙招（本项目的端到端测试全靠它，用户真人声只会更稳）。

## #14 流程纪律：一次改一堆 ≠ 一次只改一个但测八遍

- **现象**：开发中段陷入"改一个小问题→装机→重启→测→撞新问题→再改"的循环，**反复重启**引发用户强烈不满（"能不能想好了再干""多想几轮再动"）。
- **根因**：问题暴露的粒度太细（每次实测只验证一个假设），而每次装机在三星上都要付出 a11y 重绑的代价（见 #8）。
- **修复（流程制度）**：
  1. 动手前列**全量隐患清单**（一次性把能想到的相邻问题都修掉），一次装机带多个修复；
  2. **不用重启就能测的先测**（如唤醒词识别只依赖麦克风循环，a11y 死活不影响）；
  3. 测试套件化：环境就绪后一口气跑完 5 个场景（桌面唤醒/对话界面唤醒/息屏唤醒/误触/循环），全程不装机；
  4. 每个 bug 写进本文档，形成"踩坑即资产"。
- **教训**：⭐ **在"部署成本高"的环境里（要重启的嵌入式/移动端），调试节奏必须是"批量修复 + 套件化验证"，而不是"单点修复 + 单点验证"。** 排查时多想两轮、把相邻隐患一次清掉，是对用户时间的尊重。

## #15 杂项坑速查表

## #16 交付后回归：环境音把唤醒识别器"灌死"（partial膨胀）

- **现象**：交付数小时后用户报告"唤醒词突然唤不醒了"。服务进程活着、a11y绑定正常、无崩溃。
- **取证**：`adb logcat -s ButlerWake` 显示识别循环活着但输出全是**环境里的英文音视频语音**，partial被连续语音撑到30+词；用户的唤醒记录被环境音日志冲出logcat缓冲（排查本身也被干扰）。
- **根因**：Vosk全量ASR模式对连续环境音永不产生final结果，partial无界增长→解码越来越慢→实时性崩塌；用户的唤醒词混在环境音里被搅碎。**时间线对照**：环境音开播≈故障开始。
- **修复（多项一次部署）**：
  1. **语法约束识别**：`Recognizer(model, rate, "[\"[unk]\",\"codex\",...]")`——识别器只输出唤醒词表，环境音全部变成`[unk]`，partial短平快，CPU大降，唤醒在电视声里照样命中（实测）；
  2. **持久化日志** FileLog：/sdcard/.../butler.log（512KB轮转），记录服务生命周期/录音器状态/触发/挂断——logcat会被刷掉，文件不会；
  3. **防杀三件套**：onTaskRemoved划掉App后1秒闹钟拉活 + 10分钟看门狗闹钟（心跳<30秒算假死，不健康自动startForegroundService）+ 心跳时间戳；
  4. partial超长保险丝（>10词reset识别器，防御性保留）。
- **教训**：①**唤醒词场景永远用Vosk的grammar模式，不要用全量ASR**——全量模式在持续环境音下必然退化；②环境音（电视/播客）是家庭语音设备的一等公民干扰源，测试必须包含"洪灾中唤醒"场景；③logcat会被自己产品的日志刷掉，**关键状态必须落盘文件**；④"服务活着"≠"服务健康"，心跳+看门狗才能发现"线程活着但已经聋了"这类假死。
